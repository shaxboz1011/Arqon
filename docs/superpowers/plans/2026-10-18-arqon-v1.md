# Arqon v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Windows desktop app that monitors several internet links, protects game latency, combines links for downloads, and lets the user control each application.

**Architecture:** `Arqon.Core` (net10.0, no UI) holds link discovery/monitoring, scoring, rules, the chunked downloader and the steering seam. `Arqon.App` (WPF, net10.0-windows) is a thin MVVM shell over Core. Everything touching the OS sits behind an interface so tests use fakes.

**Tech Stack:** .NET 10, WPF, xUnit, `System.Net.Http` (`SocketsHttpHandler.ConnectCallback` for interface binding), WinDivert 2.2.x (experimental steering).

**Spec:** `docs/superpowers/specs/2026-10-18-arqon-design.md`

## Global Constraints

- Namespace root `Arqon`; Core assembly `Arqon.Core`, app `Arqon.App`, tests `Arqon.Core.Tests`.
- No third-party NuGet packages in Core or App (xUnit only in tests).
- All OS access via interfaces (`ILinkProvider`, `IProbe`, `ICounterReader`, `ISettingsStore`, `IWcmPolicy`, `ISteerer`).
- UI language default Uzbek (Latin); strings live in `Strings.uz.xaml` / `Strings.en.xaml` resource dictionaries.
- Dark theme colours: bg `#0F1218`, panel `#171B24`, line `#2A3040`, accent `#6C8CFF`, Wi-Fi `#4ADE80`, phone `#F59E0B`.
- Failure of steering must fall back to default Windows routing within 2 s.
- Settings file: `%AppData%\Arqon\settings.json`.

## Review Focus

- Only one link available: downloader and selector must work, not throw.
- Server without `Accept-Ranges`: single stream, correct file.
- Link disappears mid-download (phone unplugged): its chunks return to the queue; download finishes on the other link.
- Corrupt/missing settings file: app starts with defaults.
- Download interrupted and restarted: resumes, final file hash identical.

### Task 5: Interface-bound HTTP client and range downloader

**Files:**
- Create: `src/Arqon.Core/Download/BoundHttp.cs`, `RemoteFileProbe.cs`, `DownloadRequest.cs`, `DownloadProgress.cs`, `DownloadJob.cs`, `ResumeState.cs`, `RateLimiter.cs`
- Test: `tests/Arqon.Core.Tests/Download/DownloadJobTests.cs` (with `TestRangeServer` helper in `tests/.../Support/`)

**Interfaces:**
- Consumes: `LinkInfo`, `ChunkQueue`, `ByteRange`.
- Produces: `static HttpClient BoundHttp.Create(LinkInfo link)` (SocketsHttpHandler whose `ConnectCallback` binds the socket to `link.LocalAddress`); `record RemoteFileInfo(long? Length, bool AcceptsRanges, string? FileName)` via `RemoteFileProbe.ProbeAsync(Uri, HttpClient, CancellationToken)` (HEAD, fall back to `GET Range: bytes=0-0`); `record DownloadRequest(Uri Url, string DestinationPath, long ChunkSize = 4 MiB, long? SpeedLimitBps = null)`; `record DownloadProgress(long Total, long Done, IReadOnlyDictionary<string,long> PerLinkBytes, double BytesPerSecond)`; `class DownloadJob` with `Task RunAsync(DownloadRequest, IReadOnlyList<LinkInfo> links, IProgress<DownloadProgress>? p, CancellationToken ct)`, `Pause()`.

Algorithm notes: each link runs N workers (start 4, grow to 16 while aggregate throughput still rises; shrink on errors); workers pull from the shared `ChunkQueue`; a worker whose link fails returns its chunk; when the queue is empty and chunks are still in flight, idle workers race the slowest in-flight chunk (first to finish wins, duplicate discarded); writes via `RandomAccess.Write` into a pre-sized `.arqpart` file renamed on completion; `ResumeState` (JSON next to the part file) records completed ranges every 2 s; no Range support → one stream on the best link.

- [ ] **Step 1:** Tests against `TestRangeServer` (HttpListener on `127.0.0.1`, serves a 20 MiB deterministic payload, honours `Range`): (a) one fake link on loopback → file SHA-256 equals payload; (b) server variant without `Accept-Ranges` → still identical file; (c) cancel at ~30 % then rerun → completes, identical hash, and bytes requested on second run < total; (d) two fake links (both `127.0.0.1`, distinct Ids) → `PerLinkBytes` sums to total, both > 0; (e) server throttled to fail one link's requests → other link completes; (f) `SpeedLimitBps = 2 MiB/s` on a 4 MiB file takes ≥ 1.5 s.
- [ ] **Step 2:** FAIL → implement → PASS. Commit.
